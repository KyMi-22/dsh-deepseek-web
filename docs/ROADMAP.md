# 后续计划

已明确但尚未实现的方向。按我判断的优先级排列，不代表时间承诺。

## 1. 在 DSH 对话里用网页模型时，改用「临时对话 + 压缩上下文」

### 现状

在 DSH 里选「DeepSeek 网页版」模型后，这个会话会**永久绑定**一个网页对话——`bindings` 里的映射一直复用（`resolveBinding` 命中就不再新建）。之后每轮只发最新一句用户消息，靠 `parent_message_id` 让网页端自己回溯历史。

后果是网页对话会不断变长：

- 如果这个 DSH 会话是**从网页端导入的**，你在 DSH 里的新对话会写进原来那个网页对话——等于往用户的网页记录里追加内容，而用户并没有在网页端做任何事。
- 对话越长，网页端每轮要回溯的历史越多，上下文窗口被逐步占满。

### 目标

改为**一次性的临时网页对话**：

1. 首次用网页模型时不复用已有网页对话，而是新建一个**临时对话**（网页端可见，带明确标记）
2. 把原 DSH 对话**压缩成摘要**，作为临时对话的第一条消息发过去
3. 之后这个 DSH 会话在临时对话里继续
4. 原网页对话保持干净，不被追加

### 为什么这样做

- **原网页对话不被污染**：导入的对话保持导入时的样子
- **网页端仍有上下文**：靠压缩摘要，而不是靠回溯全部历史
- **上下文窗口可控**：每次都是「摘要 + 本轮」，不会无限增长

### 待定问题

- **压缩用什么模型**：纯本地算法算不了语义摘要，得调一次 LLM。用便宜的模型？还是让用户选？
- **临时对话的生命周期**：每个 DSH 会话一个（复用）？还是每轮一个（更干净，但网页端会留下一堆碎片对话）？
- **摘要质量**：压缩丢失细节后模型可能答得不连贯，要在「省 token」和「记得住」之间找平衡点。
- **命名标记**：临时对话怎么命名才不会被误认为用户的真实对话，比如 `[DSH 临时] <标题>`。
- **撤销时的清理**：临时对话要不要跟着撤销一起清掉？要清的话，得能区分「插件建的临时对话」和「用户自己建的对话」——目前的 `origin` 字段只能区分导入和本地，需要再加一种。
- **失败回退**：摘要生成失败时，是退回现有的持久绑定，还是直接报错？

### 关联

这个方向会改变 README「两个方向的同步规则」里的情况二：目前是「创建或写入对应网页对话」，改完之后变成「创建临时对话并写入」。

## 2. 中断的消息在界面上显式标注

**现状**：请求在途断开时（无法判断服务端是否已经生成），适配器选择不重试以避免重复回答，用户看到的是一条空回复。

**计划**：把这类失败记成 `interrupted`，在对话里显式显示「上次请求结果未知，可能已经生成，请手动检查」，而不是静默的空回复。

## 3. 导入内容里的网页端固定文案过滤

**现状**：导入的 assistant 消息偶尔带着网页端的固定前缀（实测出现过 `Readywhat would you like me to help with?`）。

**计划**：在 `buildSeedEvents` 里加一层过滤，把这类已知的固定文案从导入正文里剔掉。
